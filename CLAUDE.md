# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm install       # install deps
npm run dev       # dev server at localhost:3000
npm run build     # production build (next build); statically prerenders every route
npm run start     # serve the production build
```

Data refresh (registry in `scripts/data-sources.mjs`, runner `scripts/update-data.mjs`):

```
npm run data:status              # every refresh job, its last run and whether it's due
npm run data:update -- --due     # run every due auto job (or name jobs: -- worldmap-government)
npm run data:update -- <job>     # a manual job prints its checklist instead
npm run data:done -- <job>       # record a manual job as completed
npm run data:graph               # regenerate the /knowledgegraph data-sources graph
npm run data:check               # validate the registry + check every source URL responds
```

`data-sources.mjs` is the single source of truth for external data: `SOURCES` (name, URL, license token, pages that use it) and `JOBS` (the generator commands that refresh them, how often, their outputs, dependencies). `public/knowledgegraph/datasources.fol` (the default `/knowledgegraph` graph, one `<license>(<source>, <page>)` link per use) is generated from `SOURCES` — edit the registry, not the `.fol`. Any new external source or generator script gets an entry there. Last-run dates live in the committed `scripts/data-sources.state.json`. After a run, review the data diff and run `lint`/`build` before committing.

There is no test suite in this repo (no Jest/Vitest/Playwright config, no `*.test.*`/`*.spec.*` files).

`npm run lint` uses ESLint 9's flat config (`eslint.config.mjs`), which bridges `eslint-config-next`'s legacy `next/core-web-vitals`/`next/typescript` presets via `FlatCompat` (the old `.eslintrc.json` was removed as redundant). It also reuses `.gitignore` via `@eslint/compat`'s `includeIgnoreFile` so it doesn't lint `.next/` build output or `next-env.d.ts` — without that, plain `eslint .` (unlike the `next lint` CLI) has no built-in awareness of Next's build artifacts. The codebase is currently lint-clean; `npm run build`'s lint step is not suppressed, so new errors will fail the build.

There is also a `flask-app/` directory — it's the unmodified Flask quickstart boilerplate (`"Welcome to the Flask App!"`), not wired into the Next.js app or any page. Don't assume it backs any feature.

## Architecture

Next.js App Router, TypeScript, one folder per route under `src/app/*/page.tsx`. Path alias `@/*` → `src/*`.

**Every page** starts with `'use client'`, wraps its content in `src/layouts/standardLayout.tsx` via `StandardLayout({ title, main, headerMode, variant })`, and imports its own page-scoped CSS file directly (no CSS modules). `headerMode` is `'full' | 'tyro-only' | 'none'`: `'full'` renders the sticky site header (`layouts/header.tsx`: Tyro avatar + name, `/ title` breadcrumb, Work/Experience/Skills anchor links to the home page, Contact button); `'tyro-only'` is used by the heavier interactive/3D pages that want just the floating Tyro home button. `variant` is `'card' | 'plain'` (default `'card'`, a centered white surface for text pages; the home page uses `'plain'` and lays itself out). Design tokens (colors, radii, shadows, `--site-header-h`, `--content-max`, `--gutter`) live in `globals.css` `:root` — use them instead of hard-coding. Gotcha: with `'tyro-only'`, that avatar is absolutely positioned (no layout height), so a full-bleed page's `:has(.xPage) .standardlayout-main { height: ... }` override must not subtract a header height (use `100dvh` alone); `'full'`-mode full-bleed pages (`hydrogen`) subtract `var(--site-header-h)`.

Page CSS is imported globally and persists across client-side navigation, so scope every rule under the page's root class (e.g. `.home …`, `.hubbard …`, `.solitaire-container …`) — never bare element selectors like `p`/`body`/`blockquote` or generic classes like `.board`/`.card` (both have leaked across pages before). Also note several pages share class names (`hydrogen` and `brain` both use `.workArea`/`.mathDrawer`), so scope media-query overrides too. Inside the `'card'` surface (a flex column), a centered wrapper with `margin: 0 auto` needs an explicit `width: 100%`, or it shrinks to fit-content and wide KaTeX/tables push it past the viewport.

`public/TyroImages/` holds the Tyro (the cat) photos used across the site: `TyroAvatar.png` (square face crop, header/home button), `HighFive.png` (Minesweeper win), `AnOfferYouCantRefuse.png` (home contact CTA), `PuppyEyes.png` (404 page, Minesweeper loss). `HighFive.png`/`AnOfferYouCantRefuse.png` were originally HEIC files with a `.png` extension (invisible outside Safari) — make sure any new photo is a real PNG/JPEG/WebP.

**`/resume` is the de facto homepage** — `src/app/page.tsx` just renders `<Resume />`. The resume page is data-driven: the `WORK` array in `src/app/resume/page.tsx` (Research/Projects/Games cards, each with a blurb, icon and hue) is the map of "live" pages; new pages should be added there. Experience/education/skills are likewise arrays at the top of that file. Some existing pages are experimental/exploratory and deliberately commented out of that list (currently: Numerical Methods, Structural Bioinformatics, Three-Body Problem under "Class Notes"; Solitaire, Free Play under "Games") and are only reachable by direct URL — lower priority than linked pages, no need for the same polish, but check the resume page before assuming a page under `src/app` is unlinked/dead.

**Per-page structure**: pages that need it have their own scoped `components/`, `data/`, `utils/`, and/or `styles/` subfolders (e.g. `src/app/solarsystem/`). Nothing is shared across pages except `src/layouts/*` and `src/app/util.tsx`.

**Heavy WebGL/three.js pages** (`solarsystem`, `brain`) load their canvas component via `next/dynamic(() => import(...), { ssr: false })` with a loading fallback, since `three`/`@react-three/fiber` can't run during SSR. `knowledgegraph` and `threeBody` import their canvas components directly without this guard instead — that's inconsistent, not intentional; follow the `dynamic(..., { ssr: false })` pattern for any new heavy visualization page.

**Data-driven simulation pages** follow the layering seen in `src/app/solarsystem/`: a `data/` file holding per-body physical/orbital constants and display config → a `utils.tsx` with the actual math (e.g. solving Kepler's equation, or wrapping the `astronomy-engine` package for real-world positions) → `components/` that just render based on that math. Keep that data/math/render separation for new simulation-style pages rather than inlining physics into components.

Two perf/correctness patterns worth following if you touch simulation code: don't call `require(...)` or rebuild lookup tables inside a `useFrame` callback (it runs every frame, for every animated object) — hoist heavy imports and static lookup tables to module scope; and prefer `THREE.InstancedMesh` over mapping many individual `<mesh>` elements when rendering repeated identical geometry (e.g. asteroid belts, particle fields). Orbit lines (`components/Orbit.tsx`) render via `@react-three/drei`'s `<Line>` (backed by `Line2`/`LineMaterial`) rather than a plain `THREE.Line` — standard WebGL line width is clamped to 1px in most browsers regardless of the value set, so varying an orbit's visual thickness (e.g. asteroids' thinner lines vs. planets') requires the fat-line component instead.

The `solarsystem` page's on-canvas UI controls are two collapsible panels (`components/ObjectVisibilityMenu.tsx` for per-body show/hide, `components/OrbitControls.tsx` for display settings) stacked inside one shared `.solar-menu-stack` card in the top-left corner, each toggled by a `.menu-toggle-button` labeled with its own title rather than an icon. `data/regions.ts` holds the single source of truth for solar-system body groupings (inner/outer planets, asteroid belt, orbit-line colors) — both `SolarSystem.tsx` (orbit coloring) and `ObjectVisibilityMenu.tsx` (menu grouping) import from it rather than each keeping their own copy of the lists. Within the "Asteroid Belt" region group, the belt visualization itself (`bodies: ['Asteroid Belt']`) is a standalone toggle rendered above its three size-bucketed subgroups (`>300km`/`200-300km`/`100-200km`) rather than nested inside one — `RegionGroup` supports a group having both direct `bodies` and `subgroups` at once for this. Ceres and every individually-named asteroid start hidden (`DEFAULT_HIDDEN_BODIES` in `UniverseCanvas.tsx`); only the "Asteroid Belt" instanced-mesh cloud (`components/AsteroidBelt.tsx`) is visible by default. That cloud isn't a flat random ring — each particle borrows one real asteroid's orbital elements (semimajor axis, eccentricity, inclination, node/perihelion angles; Hektor excluded since it's a Jupiter Trojan, not main-belt) and lands at a random point along that specific ellipse via `utils.tsx`'s `orbitalPosition`, so the cloud approximates the belt's real 3D shape rather than a stylized disc.

Beyond the planets, everything is real data with its own generator under `solarsystem/jpl/` (raw sources cached next to it; regenerate rather than hand-edit), most of it added from Wikipedia's "List of Solar System objects" (saved at `wikipedia/Lists/`):
- **Trojans / Kuiper belt** (`components/Trojans.tsx`, `KuiperBelt.tsx`, both via the shared `OrbitSwarm.tsx` InstancedMesh): `data/trojans.ts` (`generateTrojans.py`; Jupiter H ≤ 14, Neptune co-orbitals filtered to real L4/L5) and `data/kuiperBelt.ts` (`generateKuiperBelt.py`; SBDB TNOs H ≤ 8, split at a = 50 AU). Each object is propagated from its real elements to the simulation date — random phases (like the main-belt cloud) would smear the Trojan swarms into a ring.
- **Named small bodies** (NEOs, other planets' trojans, centaurs, Orcus/Quaoar/Gonggong/Sedna, KBOs, scattered/detached): `data/smallBodies.ts` (`generateSmallBodies.py`: diameter/albedo from each body's Wikipedia infobox under `wikipedia/SmallBodies/`, orbits from SBDB), mapped to the asteroid/dwarf-planet body shape by `data/smallBodies.display.ts` so they render and focus through `Planet.tsx`; all start hidden.
- **Comets** (`components/Comets.tsx`): `data/comets.ts` (`generateComets.py`, SBDB perihelion elements, works for hyperbolic 2I/3I; prints its error vs Horizons — Tempel 1 drifts most). Position/orbit real; tail sizes illustrative (ion tail anti-sunward, dust tail trailing).
- **Heliosphere + probes** (`components/Heliosphere.tsx`, `Spacecraft.tsx`): `data/spacecraft.ts` (`generateSpacecraft.py`, Horizons trajectories of Pioneer 10/11, Voyager 1/2, New Horizons). The termination shock / heliopause surfaces pass exactly through the Voyagers' actual crossing positions (dates from their Wikipedia articles) via a fitted scale plus one north–south asymmetry term (Voyager 2's termination shock was 10 AU closer); the nose points into the IBEX-measured interstellar inflow (ecliptic 255.7°, 5.04°; Swaczyna et al. 2023, abstract saved in `solarsystem/literature/`), not along the galactic velocity — the local interstellar gas orbits the Galaxy almost as fast as the Sun. The comet-like shape itself is modelled.
- **Galactic motion**: `data/galacticMotion.ts` (hand-curated from `wikipedia/Galaxy/`: Oort constants, the Sun's peculiar motion, 83 Myr vertical period — its header lists how the derived galactic year/epicycle/99 pc oscillation match the articles). `utils.tsx`'s "Galactic motion" section integrates the Sun's orbit in a power-law rotation curve fitted to the Oort constants plus a harmonic vertical potential. `components/GalacticTrails.tsx` (Display Options → Galactic Path) draws every shown body's real helix over the last 1–1000 years as a tracer: heliocentric position at each past instant + the Sun's galactic velocity × elapsed time, built in a frozen frame and slid back each frame, rendered as a screen-space ribbon (its own shader, not drei `<Line>`) whose pixel width is set by body kind (Sun > planets > dwarfs > small bodies) and tapers/fades toward the tail. Enabling a path while time is at Live starts it at 1 yr/sec; `components/SunGalacticOrbit.tsx` draws the last 250 Myr of the Sun's orbit in the Milky Way view. Nothing is exaggerated, so the helices are long and thin (the Sun moves ~48 AU/yr); the camera far plane is 2e6 for the 1000-year trails.
- Minor-body rings (Chariklo, Haumea, Quaoar) are in `data/rings.ts`; dwarf-planet and extra Saturn/Pluto moons go through the same moon generator (`generateTs.py`, with Wikipedia a/P/size for moons JPL's tables lack).
`orbitalPosition()`'s epoch branch solves Kepler's equation with Newton's method — the old 5-step fixed-point loop was tens of degrees off for high-eccentricity orbits (Sedna, 2017 OF201). drei `<Html>` overlays ignore a hidden parent `<group>`, so mount them conditionally (see `Heliosphere.tsx`), and they keep projecting anchors that are behind the camera (mirrored on screen) — hide those per frame. The heliosphere's boundary tags sit on each bubble's silhouette and only show while the camera is outside that boundary; clicking one opens its info card and Voyager crossing markers.

Focusing one of the 8 major planets renders a true-to-scale 3D cutaway (core/mantle/crust/atmosphere), plus a mirrored `.solar-menu-stack-right` card in the top-right holding `LayerVisibilityControls.tsx` (Show Atmosphere/Show Crust toggles) and two collapsible panels: `LayerCrossSection.tsx` (core→atmosphere) and `AtmosphereCrossSection.tsx` (troposphere→exosphere, shown only while atmosphere is toggled on). Hovering a layer (in the 3D view or in `LayerCrossSection.tsx` itself) surfaces its data only in that right-side panel — there's no separate floating 3D tooltip. `data/planetStructure.ts` is the single source of real per-planet data — layer proportions (`radiusFraction`), sourced from each planet's saved Wikipedia page under `wikipedia/Planets/<Planet>/` (the same `data-mw` JSON-extraction technique used for `data/asteroids.ts`) rather than fabricated for visual clarity. Core/mantle sub-layers (`innerCore`/`lowerMantle`) and `atmosphere.layers` are added only where the source directly cites a sub-boundary, not for every planet — see that file's header comment for which planets have them and why. `getLayerSegments()` is the shared function both the 3D renderer and the 2D panels call so they can't drift out of sync; `Planet.tsx`'s `Shell` component is the reusable one-radial-layer mesh (2 outer-surface pieces + 3 cut-face rings) that both core/mantle and their sub-layers render through.

Moons (shown only for the focused planet, `components/Moon.tsx`) are listed by name in `data/planets.tsx` and drawn at their planet's true scale (km × planetSize / planet's real equatorial radius, so Earth's Moon sits 60 Earth radii out — camera framing in `CameraController.tsx` therefore only fits moons within ~8 planet radii). Positions are real for the simulation's date: Earth's Moon and the Galilean four come from astronomy-engine; every other moon uses `data/moonElements.ts`, generated by `jpl/generateTs.py`, which anchors an orbit to JPL Horizons state vectors (cached raw under `jpl/horizons/`) and prints its own error vs Horizons for 2020–2040 (≲3°, except Mimas ~15° and Hyperion ~25° from resonances). Don't switch back to JPL's published mean-elements table alone — that was tried and Saturn/Uranus rows didn't reproduce Horizons even at J2000 (Uranus's IAU "north" pole is also the retrograde one; use its rotational pole). Shapes/albedos/colors/tidal locking live in the hand-curated `data/moonAppearance.ts`. Moon orbit lines are plain `THREE.Line`s, not drei `<Line>` — mounting/unmounting several drei Lines on every planet switch reliably lost the WebGL context.

Internal-layer colors are shared across planets via `LAYER_COLORS` in `data/planetStructure.ts` (same slot = same color on every planet, in both the 3D cutaway and the 2D panels); don't reintroduce per-planet hex colors. The right-side cross-section panels have fixed-height legend/detail areas on purpose: when the detail area resized with the hovered layer, the Atmosphere panel below shifted under the cursor and the hover flickered between segments.

The page has four nested models — Local Group ⇄ Milky Way ⇄ Solar System ⇄ planet — reachable from the tab nav or by scroll-zooming past a model's edge (`components/ScaleTransitions.tsx`: camera-to-pivot distance thresholds per model; it sets `scaleTransition.entry` in `utils.tsx` so `CameraController` arrives at the matching end of the next model, e.g. zooming out of the Solar System lands in the Milky Way zoomed in on the Sun). The Solar System stays mounted (hidden) in the galaxy views — unmounting it and rendering straight on lost the WebGL context — and the Milky Way's Galactic Objects menu mounts 1.5 s after the view does, because swapping the menu stack's contents in the same commit as that scene switch also reliably lost the context (even with a bare `<div>`).

The "Milky Way" tab (`components/MilkyWayField.tsx`, 10 scene units/kpc, same galactocentric axes as the Local Group) is built from `data/milkyWay.ts`, generated by `galaxy/generateMilkyWay.py`: the spiral arms are Reid et al. 2019's maser-parallax log-spiral fits (Table 2 parsed from the paper's TeX source in `literature/reid2019/`; drawn at full density over the measured azimuths, extrapolated ±60° at lower density), and ~520 objects (globular/open clusters, supernova remnants, black holes, neutron stars, star-forming regions, Messier nebulae, nearest stars) come from the Wikipedia lists reached from "Lists of astronomical objects" (saved under `wikipedia/Galaxy/Lists/`). Satellite galaxies within 300 kpc reuse `data/localGroup.ts`. Disk scale length comes from the infobox half-light radius, the bar from Wegg 2015. Particle size is capped in px (`starParticles.ts` `maxPx`) so the disk doesn't balloon when zoomed in on the Sun; the orbit pivot eases from the Sun to the Galactic Centre with zoom.

The solarsystem page's "Local Group" tab (`components/GalaxyField.tsx`, rendered inside the same `<Canvas>` when `focus === 'cosmic'`) draws the real Local Group at true relative scale, not stylized spheres. `data/localGroup.ts` is generated, not hand-written: `localgroup/generateTs.py` parses McConnachie's "Nearby Galaxies" catalog (saved as `localgroup/NearbyGalaxies_Jan2021_PUBLIC.fits`, a FITS binary table read with `struct` since astropy isn't installed) into RA/Dec, distance, absolute magnitude, half-light radius, ellipticity, PA and HI mass for every galaxy within 1.5 Mpc — regenerate rather than hand-edit. The catalog has no row for the Milky Way or Andromeda and no sizes/orientations for M33/LMC/SMC, so those live in the hand-curated, cited `data/localGroupHosts.ts`. `utils.tsx`'s Local Group section does the math (equatorial→galactic rotation, Sun's galactocentric offset, disk axes from inclination/PA, Plummer/exponential-disk particle sampling) and `buildLocalGroup()` returns one merged particle buffer; the component renders it as a single additive `<points>` with a custom shader that clamps sub-pixel points to a minimum size and dims them instead (so far-away dwarfs fade rather than vanish). The Milky Way star-map background is hidden in this view since the camera is outside the galaxy.

Math-heavy text pages (`structuralbioinformatics`, `hubbardmodel`) render LaTeX via `react-katex`'s `<BlockMath>`/`<InlineMath>` plus `katex/dist/katex.min.css`.

The `hydrogen` page's periodic table (`components/PeriodicTable.tsx`, Z=1-36 selectable) drives every visualization on the page via a `selectedZ`/`Z` prop threaded down from `page.tsx`; it's collapsed by default behind a `.elementBadge` button in the top nav (`page.tsx`'s `energyNav`) and auto-collapses again on any selection (`periodicTableCollapse` in `styles/HydrogenAtom.css`). The Spectrum tab (`components/HydrogenSpectrum.tsx`) branches on `Z`: hydrogen (Z=1) draws its lines from the exact Rydberg formula (`buildLines`, hydrogen's real named series); every other element instead uses real measured lines (`buildRealLines`, grouped/colored by ionization stage) from `data/nistSpectralLines.ts`, sourced from NIST's Handbook of Basic Atomic Spectroscopic Data "Persistent Lines" tables — see that file's header comment for the sourcing/units/caveats. That data file is generated, not hand-written: `nist/nistScraper.py` fetches and saves each element's raw source pages under `nist/<Element>/` (same saved-source-for-provenance convention as `solarsystem/wikipedia/`), and `nist/generateTs.py` converts the parsed JSON straight into the `.ts` data file — regenerate both rather than hand-editing entries if the source data changes. (`globals.css` no longer forces a color on `p, li, span`; text inherits from its container.)

The `worldmap` page is a d3 SVG map (countries → admin-1 subregions → admin-2 districts) with a side panel per selection (Wikipedia articles fetched client-side, plus Government/Economy/Demographics tabs) and a "Color map by" choropleth control. All its data is static files under `public/worldmap/`, generated by scripts in `scripts/` — regenerate rather than hand-edit: `build-admin1.mjs` (Natural Earth admin-1 → per-country TopoJSON, also copies world-atlas `countries-50m.json`), `build-admin2.mjs` (Natural Earth US counties + geoBoundaries ADM2 → per-subregion TopoJSON), and `build-worldmap-db.mjs` (Wikidata, Wikipedia legislature infoboxes and the World Bank API → the CSV database in `public/worldmap/db/`, schema in its `README.md`). Shapes are keyed by `countrySlug()` (kept identical in `scripts/worldmap-geo.mjs` and `src/app/worldmap/lib/countryNames.ts`). Party seat counts come from rendered Wikipedia infoboxes, not Wikidata (whose P1410 data was stale/double-counted), and a chamber is only kept if its parties sum to its seat total.

The worldmap's time slider (`components/TimeSlider.tsx`, 1886–2019 plus "Today") swaps the country layer for CShapes 2.0 historical borders (`public/worldmap/history/countries.json`, built by `scripts/build-history.mjs`, which also writes `db/entities.csv`/`db/entity_periods.csv`). CShapes keys a territory by one Gleditsch–Ward code across regime changes and names colonies by their modern name, so `scripts/worldmap-history-names.mjs` hand-curates which Wikipedia article each date range is (Gold Coast → Ghana, Russian Empire → … → Russia); the build checks every title against Wikipedia and fails on a missing one. Historical countries are keyed `gw-<code>`, so a selection follows a territory across years; when it disappears (or when crossing to/from Today) the page moves the selection to whichever shape holds the old capital. A year's map shows borders as of 1 July (CShapes puts uncertain dates on 1 January). Subregions, districts and the choropleth are present-day only. Don't add mapshaper's `-clean` to that build: country-periods overlap each other by design, and `-clean` deletes the overlaps. CShapes is CC BY-NC-SA 4.0 (non-commercial).

`next.config.ts` reads `NEXT_DIST_DIR` (default `.next`) so a second dev server can build into its own folder — several `next dev` processes sharing `.next` corrupt each other's cache (symptoms: `ENOENT …_document.js`, `ChunkLoadError`, pages 404ing). `.claude/launch.json`'s `worldmap-isolated` config uses this.

Per-page static assets live under `public/<pageName>Images/` (e.g. `public/solarsystemImages`, `public/hubbardmodelImages`, `public/methanogensImages`), matching the page's route name.

The `brain` page renders `public/brainImages/brain.glb`, generated (not hand-made) in two steps: `python scripts/brain/cerebra_meshes.py` turns the CerebrA atlas (Manera et al. 2020, CC0: Mindboggle-101/DKT labels on the MNI-ICBM2009c template, 51 regions per hemisphere) into one smoothed mesh per left/right label under `scripts/.cache/cerebra/meshes/` (needs numpy, scipy, scikit-image, h5py), then `node scripts/build-brain-model.mjs` simplifies them with meshoptimizer into the GLB. Neighbouring labels are meshed against each other (each label's blurred mask minus the best competing label's), so regions share boundaries with no gaps; don't go back to meshing each label's mask on its own. CerebrA has no white-matter label, so the script derives it from unlabelled voxels inside the cerebrum that are brighter than cortex on the T1 template (a fill alone also captures the fluid in the Sylvian fissure and covers the insula). Meshes are named `L-<region>`/`R-<region>` after CerebrA's label names; `src/app/brain/data/regions.ts` describes each region once (description, Wikipedia title, optional `left`/`right` lateralization notes, and `refs` to open-access papers verified on OpenAlex) and derives per-region colors from the group hue (keep hues in 0-359: three.js silently turns `hsl(-2, ...)` white). The GLB stores no normals on purpose (gltf-transform's `normals()` unwelds into flat shading); `BrainModel.tsx` computes smooth ones on load.
